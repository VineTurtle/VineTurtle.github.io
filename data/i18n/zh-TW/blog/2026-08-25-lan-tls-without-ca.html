在開發 VinePalmaFlow（我們的本地優先專案管理工具）的區域網路同步功能時，遇到了一個教科書上很少講的問題：兩臺區域網路裝置之間要建立加密連線，可是既沒有 CA 簽發的證書，也沒有域名，甚至對方的系統時鐘都可能不準。Web PKI 那套信任模型在這裡完全失效。這篇筆記記錄 rustls 0.23 上的三個坑，以及我們最終的應用層認證設計。

📦 問題背景

VinePalmaFlow 的同步架構是：mDNS 發現裝置 → TLS 1.3 加密通道 → WebSocket 交換 JSON 訊息。安全目標是「只有互相配對過的裝置才能同步資料」。聽起來簡單，但每一個前提條件在區域網路裡都不成立：

  • ❌ 沒有 CA：不可能給區域網路裡的裝置簽發受信任證書
  • ❌ 沒有域名：SNI 的 ServerName 不能用字串構造
  • ❌ 時鐘不可信：新裝機的裝置 BIOS 時鐘可能停在幾年前
  • ✅ 唯一可信的：使用者本人當場看著兩塊螢幕輸入配對碼

坑一：rustls 0.23 必須顯式安裝 crypto provider

rustls 0.23 把加密後端拆成了可插拔的 provider，不安裝就直接 panic。這是升級後最先撞上的牆：

// 程序入口处，只装一次
rustls::crypto::ring::default_provider()
    .install_default()
    .expect("failed to install rustls crypto provider");

坑二：IP 直連的 ServerName 構造

Web 教材裡客戶端都是 ServerName::try_from("example.com")，但區域網路裡我們只有 IP。字串形式的 IP 會在握手時被拒絕，必須使用專門的變體：

use rustls::pki_types::ServerName;

// ❌ ServerName::try_from("192.168.1.5")? —— 当作域名处理，校验失败
// ✅
let server_name = ServerName::IpAddress(ip.into());

另外對空地址與 0.0.0.0 要回退到 127.0.0.1，否則 mDNS 解析尚未完成時發起的首次同步會直接報錯。

坑三：證書有效期的時鐘偏移

自簽證書預設把 not_before 設為生成時刻。設想裝置 A 時鐘正常、裝置 B 時鐘慢了一天：B 生成證書 → A 校驗時發現「證書還未生效」→ 握手失敗。更糟的是這種問題只在特定兩臺裝置間出現，極難復現。解法簡單粗暴——把有效期視窗拉滿：

let mut params = rcgen::CertificateParams::new(vec![])?;
params.not_before = rcgen::date_time_ymd(2020, 1, 1);
params.not_after  = rcgen::date_time_ymd(2099, 12, 31);
// 证书与私钥以 DER 落盘，设备生命周期内复用，不再重签

🔑 信任模型：把認證下沉到應用層

放棄證書鏈校驗後，兩端各掛一個自定義 verifier（rustls 的 danger trait）：客戶端「接受任意服務端證書」，服務端「強制索要客戶端證書」。TLS 只負責加密，身份認證完全交給上層：

  • 每臺裝置首次啟動時生成自簽證書，CN 欄位寫入裝置 ID
  • 握手完成後，服務端從對方客戶端證書 DER 裡解析出 CN，作為「認證後的裝置身份」
  • 所有同步訊息都要求該 ID 在信任列表 devices.json 中，訊息體裡聲稱的 id 不作數
// 服务端：从客户端证书提取真实身份
fn cert_common_name(cert_der: &[u8]) -> Option<String> { /* 解析 CN */ }

// 消息处理时以证书 CN 为准，而非消息体里的 id
if !is_trusted(&cert_peer_id) {
    return reject("device not paired");
}

配對本身靠雙向 6 位配對碼：兩臺裝置各自螢幕顯示一個碼，使用者互相輸入對方的碼，雙向核對通過才寫入信任列表。這本質上是 TOFU（Trust On First Use）+ 人工帶外驗證的組合，安全性等價於藍牙配對。

順手做了一個加固：在 verify_tls12_signature 裡直接返回錯誤，停用 TLS 1.2，只允許 1.3 握手，少一類降級攻擊面。

✅ 用測試鎖住安全模型

這類「自定義 verifier + 應用層認證」的設計很容易在重構中被悄悄破壞，我們為它寫了專門的迴歸測試：偽造證書 CN（不在信任列表）的推送必須被拒絕、未配對裝置的 sync_push 必須返回錯誤、TLS 迴環握手必須成功。安全邏輯一旦寫好，就讓測試替你站崗。

📝 小結

區域網路點對點加密的正確姿勢：自簽證書承載身份、TLS 只管加密、認證下沉應用層、配對碼完成 TOFU、有效期視窗拉滿容忍時鐘漂移。整套設計在 VinePalmaFlow 裡大約 300 行 Rust，沒有引入任何 CA 基礎設施，卻提供了與雲端服務相當的傳輸安全。
