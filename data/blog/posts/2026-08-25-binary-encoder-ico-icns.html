给 VinePalmaToolbox 做「图片格式转换」工具时遇到了一个尴尬：浏览器 Canvas 的 toBlob() 只支持 PNG / JPEG / WebP，而用户偏偏最常要求「把这张图转成 ICO 图标」。找遍 npm，好用的 ICO 编码库寥寥无几，ICNS（macOS 图标）更是没有维护良好的纯前端实现。最后我们决定：照着格式规范，用 DataView 一个字节一个字节自己拼。

🧱 ICO：最「简单」的容器格式

ICO 本质是一个「PNG 打包器」：文件头 + 目录 + 图片数据。Vista 之后允许直接内嵌 PNG 数据，这大大简化了实现——用 Canvas 把原图缩放到各尺寸导出 PNG，再拼装即可：

// 文件头：6 字节，小端
writeU16(0);        // 保留字段，必须为 0
writeU16(1);        // 1 = ICO，2 = CUR
writeU16(count);    // 目录项数量

// 每个尺寸一个目录项：16 字节
writeU8(size === 256 ? 0 : size);  // 宽（256 写 0！）
writeU8(size === 256 ? 0 : size);  // 高
writeU8(0);          // 调色板数
writeU8(0);          // 保留
writeU16(1);         // 色彩平面（ICO）
writeU16(32);        // 色深
writeU32(png.length);// 数据长度
writeU32(offset);    // 数据偏移

三个容易翻车的细节：① 256px 的宽高要写 0 而不是 256（一个字节装不下，规范约定 0 表示 256）；② 偏移量必须累加计算，目录区之后第一个数据块的偏移是 6 + 16×count；③ ICO 与 CUR 的区别除了类型字段，CUR 还要把「色彩平面/色深」字段改写为热点坐标（hotspot x/y）——鼠标指针的点击位置就存在这两个字段里。

🍎 ICNS：大端序的另一套世界

ICNS 是 macOS 的图标格式，与 ICO 最大的不同是大端序，以及用 4 字节 ASCII 类型码标识尺寸：

writeU32(0x69636e73);  // 'icns' 魔数（大端）
writeU32(totalLength); // 整个文件长度
// 每个尺寸一个块：
// 4 字节类型码 + 4 字节块长 + PNG 数据
writeType('icp4');   // 16x16
writeType('ic07');   // 128x128
writeType('ic10');   // 512x512（或 1024@2x）

调试时最费时间的是「文件长度」字段：必须等于所有块长之和加 8 字节头，写错一个字节 macOS 直接拒绝加载，而且不报错。

🔍 通用经验：用十六进制编辑器验收

二进制代码的正确性没法 console.log 出来看。我们的验收流程是：生成文件 → xxd 查看头十六个字节 → 对照 spec 逐字段核对 → 再用系统工具（file 命令、macOS 预览、Windows 资源管理器）交叉验证。file x.ico 输出 "MS Windows icon resource - 5 images" 的那一刻，比任何单元测试都踏实。

📝 小结

这轮手搓的收获：二进制格式没有想象中神秘——ICO 是「数组 + 偏移」，ICNS 是「TLV 列表」，真正的工作量在于边界约定（256 写 0、长度含头不含头、大端小端）。这些约定在 spec 里往往只有半句话，却是全部的坑所在。VinePalmaToolbox 的图片转换工具现在支持 PNG/JPEG/WebP/BMP/ICO/CUR/ICNS/DDS 互转，全部核心编码逻辑不超过 400 行 TypeScript。
