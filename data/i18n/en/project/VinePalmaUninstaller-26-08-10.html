Uninstalling software on Linux has never been a relaxing affair: APT, Flatpak, Snap, Docker, AppImage... every source demands its own set of commands to memorize, and manually installed software isn't even in the package manager's registry. Worse, even after a clean apt purge, leftovers pile up in ~/.config, ~/.cache and ~/.local/share, quietly filling the disk over time — and all you ever get is a curt "uninstall failed" or "uninstalled but residue remains".

So our VineTurtle Studio dev team designed and built this Linux uninstaller with Tauri + Vue, bringing software from six sources — APT, Flatpak, Snap, Docker, AppImage and APM — under one graphical interface, balancing "uninstall thoroughly" against "never delete the wrong thing".

Background and goals

Linux's software ecosystem flourishes, but that brings fragmentation in management: the built-in app store only manages one source; the command line expects you to memorize a different uninstall syntax for each; and Debian-family packages leave an "rc state" record after removal — the Windows-registry-residue equivalent — which ordinary users have no way to tackle. We wanted a graphical uninstaller for ordinary people: one scan, all six sources at a glance; before you click uninstall, a simulated preview tells you what will be affected; tick the leftover files and clean them all in one go — no command line anywhere, and system components are never touched recklessly.

Architecture

VinePalmaUninstaller uses Tauri 2 as the app framework, with a Vue 3 + Vite front end and a Rust backend providing native capabilities. All scan, simulate and uninstall logic that touches the system lives on the Rust side: installed software from each source is aggregated through commands like dpkg-query, flatpak list, snap list and docker images; operations needing root (such as apt purge) escalate dynamically through pkexec, so even ordinary users can perform system-level uninstalls from the interface.

Background processes run uniformly on tokio's async executor with timeout protection, so one stuck command never freezes the whole interface; deletion flows go through "server generates plan → front end ticks items → server whitelist re-validation" — the deletable paths only ever come from a freshly regenerated server-side plan, so submitting arbitrary paths can't cause accidental deletion.

Core capability: unified scanning of six sources

APT: reads all installed packages with sizes and descriptions via dpkg-query, approximating install time from the mtime of .list files under /var/lib/dpkg/info, and hides system libraries, kernels and dependencies by default. Flatpak and Snap: list apps through their respective package managers, parsing install time and size from the app directories and snap file metadata. Docker: scans local images with size and creation time parsed, and automatically removes containers referencing an image before uninstalling it. AppImage and manual installs: these never register with a package manager, so we scan for AppImage files in common directories like ~/Applications and /opt, and identify entries whose .desktop launcher Exec points at manually installed paths. APM (Amber Package Manager): parses install info from the dpkg status file inside the container, then matches UI launchers to container data one-to-one via desktop entries of the "apm run <pkg>" form under /usr/local/share/applications.

Risk levels & user-level filtering

We don't guess danger from package names; we parse the real data of /var/lib/dpkg/status and extended_states: counting how many installed packages reverse-depend on each package, and flagging Essential and required-priority components as life-or-death system pieces. From this data, every app gets one of four risk labels — low / medium / high / critical: Essential or required priority means critical (core), being depended on by 8+ packages means high risk, and GUI apps default to low risk. The interface's default "simple mode" shows only user-level software (packages with a GUI entry); system libraries, kernels and CLI tools stay hidden. "Advanced mode" reveals everything with risk labels, plus a prominent risk banner and cascading-impact warning before any uninstall.

The uninstall plan: preview first, execute second

Clicking uninstall doesn't fire off commands directly — the server first generates a complete uninstall plan: for apt packages, apt-get purge runs in simulation mode and the to-be-removed package list is parsed out; if other components would be swept along, the plan warns explicitly "will also remove N related packages". Execution carries the AutomaticRemove=0 option — apt is never allowed to auto-remove dependencies; only the target package itself is touched. The plan lists every command that will run and whether it needs authorization, and groups leftover files by config / cache / data / system: ticked means deleted, unticked means kept — the user holds complete control over every step.

Residue cleanup & orphan dependencies

For the pain of "incomplete uninstalls" we did two things. First, we identify "rc state" packages in dpkg — already uninstalled but leaving config records behind — and a single dpkg --purge wipes the residual records clean. Second, for every app we scan the common standalone directories (~/.config, ~/.cache, ~/.local/share, ~/.local/state, ~/Applications, /opt) and recognize the app's own config directories via "package-name variant matching" — case-insensitive, hyphen/underscore equivalent — so apps that "changed their name to hide" are still found. Exact-hit directories are ticked by default; fuzzy hits that merely "contain" the name stay unticked by default, and unrelated software is never touched. Orphan dependency cleanup is built in too: autoremove's removal list is previewed first and executed only after confirmation.

Safe by design: never delete the wrong thing

For a tool that deletes files, safety is the bottom line. Beyond the "plan is the whitelist" mechanism, the backend stacks more defenses: a FORBIDDEN path table blocks /, /home, /etc, /usr, /var and other critical system directories plus their immediate children; deleting protected roots like .config, .cache and .local under home is refused; paths containing dangerous components like .. are rejected; and two protection switches — "keep user config" and "keep system config" — instantly filter out ticked paths that fall inside system directories. After every uninstall the dpkg database cache reloads, so reinstalled software is recognized correctly and interface data never goes stale.

Experience details

The interface is dark-themed: lists sort by name / install time / size used / risk level with ascending-descending toggles, plus keyword search and per-source filtering; every app gets its real icon resolved from dpkg file manifests, icon themes, Flatpak/Snap export directories, or even the icon tree inside APM containers; the top bar shows the current distro and architecture, the residue page carries its own count badge, and actions finish with Toast feedback and an automatic list refresh. Icon resolution also has multi-level caching and batched loading — scanning thousands of packages stays smooth.

Pitfalls we hit

Development stepped on plenty of Linux ecosystem landmines: apt-get's simulation output uses two different prefixes across versions — "Removing" and "Purg" — and both must be parsed; combining purge with --no-install-recommends throws a "not understood" error unless the argument order and options are adjusted; dpkg output can embed newlines inside package descriptions and wreck the parsing; docker image sizes carry GB/MB suffixes and flatpak sizes carry thousand separators, each needing its own parser; icon fuzzy matching must beware generic directory names, and icon names shorter than 3 characters never participate in matching. All of these are pinned down by unit tests as regression guards.

Cross-platform & packaging

The project builds on Tauri 2; the artifacts are deb and AppImage — the former declares libwebkit2gtk-4.1 and libgtk-3 dependencies and ships a custom desktop-entry template. The front end builds with Vite, the Rust backend compiles to a native binary; the whole app starts fast, uses little memory, and depends on no heavyweight runtime like Electron.

Closing words

VinePalmaUninstaller is at 1.0.0. As an open-source VineTurtle Studio project, we hope it proves that uninstalling on Linux can be as intuitive as on mobile: safe, thorough, and leaving no loose ends. Support for more distros and package managers, and broader residue recognition, are on the way; suggestions on GitHub are always welcome — let's make it better together.
