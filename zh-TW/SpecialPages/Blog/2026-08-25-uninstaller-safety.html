解除安裝器的安全設計：Linux 上絕不誤刪的三重防線

📅 2026年8月25日⏱ 約 5 分鐘
#Rust#Linux#安全設計#VinePalmaUninstaller

開發 VinePalmaUninstaller（我們的 Linux 圖形化解除安裝器）時，最常被問的問題不是「能解除安裝什麼」，而是「會不會刪錯」。一個以刪除為核心能力的工具，安全性不是特性，是底線。這篇筆記拆解我們的三重防線設計，以及 pkexec 提權路上踩的輸出解析坑。

防線一：計劃即白名單

點選「解除安裝」並不是直接執行命令。後端先生成一份完整的解除安裝計劃：對 APT 包先以模擬模式執行 apt-get -s purge，解析出將被移除的包列表；對殘留檔案，逐條列出將刪除的路徑。前端展示這份計劃，使用者勾選後提交。

關鍵在於：前端提交的勾選結果不被信任。執行時後端會重新生成一遍計劃，把提交的路徑與重新生成的計劃求交集——交集之外的一個位元組都不會動。就算有人繞過介面偽造請求提交 /etc/passwd，它也不在服務端生成的計劃裡，直接被丟棄：

// 执行时：以服务端重新生成的计划为准
let plan = build_plan(pkg)?;               // 重新生成
let allowed: HashSet<_> = plan.files.iter().collect();
for path in user_selected {
    if !allowed.contains(path) { continue; }  // 不在计划内，忽略
    trash_or_delete(path)?;
}

防線二：路徑黑名單與危險元件攔截

即便路徑出現在計劃裡，還有一層靜態黑名單兜底：/、/home、/etc、/usr、/var 等 14 個系統關鍵目錄及其直系子目錄一律拒絕；使用者家目錄下的 .config、.cache、.local 等「配置根目錄本身」也拒絕刪除（裡面的具體軟體目錄可以刪）；含 .. 元件的路徑直接判非法——正常路徑不需要它，需要它的必然不懷好意。

防線三：保護開關與保守的預設勾選

殘留掃描通過「包名變體匹配」識別軟體自己的目錄（大小寫不敏感、連字元/下劃線等價），但匹配分兩檔：精確命中預設勾選，僅「包含」關係的模糊命中預設不勾選——寧可漏刪，不可誤刪。介面上還有「保留使用者配置」「保留系統配置」兩個開關，勾選的路徑若落在系統目錄會被即時過濾。三道防線各司其職：白名單管「來源可信」，黑名單管「路徑合法」，開關管「使用者意圖」。

🧪 提權的玄學：pkexec 與 LC_ALL=C

系統級解除安裝需要 root，我們用 pkexec 動態提權（彈出圖形化密碼框，比 sudo 友好）。這裡有個隱蔽的坑：apt 的輸出文案依賴 locale，中文環境下「正在移除」這樣的字首沒法解析。解法是給所有外部命令強制 LC_ALL=C，然後同時相容三種英文字首：

export LC_ALL=C
apt-get purge -y pkg
# 不同版本输出可能是：
#   Removing pkg ...
#   Purg pkg
#   Purging config files pkg
fn extract_removed(line: &str) -> Option<String> {
    for prefix in ["Removing", "Purg", "Purging"] { /* ... */ }
    None
}

另一個細節：判斷自身是否 root 不能調 getuid()——Tauri 行程的環境變數可能干擾 libc 結果，直接解析 /proc/self/status 的 Uid: 行更可靠。所有外部命令都套 tokio timeout，個別卡死的 dpkg 前端不能拖死整個介面。

📊 附贈：手撕 dpkg 資料庫算風險

風險等級（critical/high/medium/low）不靠猜包名，而是直接解析 /var/lib/dpkg/status：按空行分段、空格縮排續行，只認 install ok installed 狀態，統計每個包被多少已安裝包反向依賴，結合 Essential 與 Priority: required 欄位判定核心元件——Essential 包直接標 critical，被 8 個以上包依賴標 high。真實資料勝過一切啟發式規則。

📝 小結

刪除類工具的安全設計可以總結為一句話：前端不可信、計劃即白名單、黑名單兜底、預設保守。使用者把系統交給你，你遞回去的每一把刀都必須有鞘。
