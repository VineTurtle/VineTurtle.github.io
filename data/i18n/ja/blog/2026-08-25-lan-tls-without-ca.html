VinePalmaFlow（私たちのローカルファーストなプロジェクト管理ツール）の LAN 同期機能を開発中、教科書がめったに語らない問題に行き当たりました：2 台の LAN デバイス間で暗号化接続を確立したいのに、CA が発行した証明書もドメイン名もなく、相手のシステム時計が狂っていることすらある。Web PKI の信頼モデルはここでは完全に機能しません。このノートは rustls 0.23 で踏んだ 3 つの落とし穴と、最終的なアプリケーション層認証の設計を記録します。

📦 問題の背景

VinePalmaFlow の同期アーキテクチャは：mDNS がデバイスを探索 → TLS 1.3 の暗号化チャネル → WebSocket で JSON メッセージ交換。セキュリティの目標は「相互にペアリング済みのデバイスだけがデータを同期できる」こと。単純に聞こえますが、前提条件はどれも LAN の中では成立しません：

  • ❌ CA がない：LAN 内のデバイスに信頼された証明書を発行することは不可能
  • ❌ ドメインがない：SNI の ServerName は文字列では構築できない
  • ❌ 時計が信頼できない：新規組み立てマシンの BIOS 時計は数年前で止まっていることもある
  • ✅ 唯一信頼できるもの：2 台の画面を見ながらペアリングコードを打ち込むユーザー本人

落とし穴 1：rustls 0.23 は crypto provider の明示的インストールが必須

rustls 0.23 は暗号バックエンドをプラガブルな provider に分割し、インストールしないままでは即 panic します。アップグレード後に最初にぶつかる壁：

// 程序入口处，只装一次
rustls::crypto::ring::default_provider()
    .install_default()
    .expect("failed to install rustls crypto provider");

落とし穴 2：IP 直結接続の ServerName 構築

Web の教材ではクライアントは ServerName::try_from("example.com") と書きますが、LAN の中にあるのは IP だけです。文字列形式の IP はハンドシェイクで拒否されるため、専用のバリアントを使う必要があります：

use rustls::pki_types::ServerName;

// ❌ ServerName::try_from("192.168.1.5")? —— 当作域名处理，校验失败
// ✅
let server_name = ServerName::IpAddress(ip.into());

なお、空アドレスと 0.0.0.0 は 127.0.0.1 にフォールバックすること。さもないと、mDNS 解決が完了する前に送出された最初の同期が即エラーになります。

落とし穴 3：証明書有効期限と時計ずれ

自己署名証明書は既定で not_before を生成時刻に設定します。デバイス A の時計は正常、デバイス B の時計は 1 日遅れ、という場面を想像してください：B が証明書を生成 → A が検証するとき「証明書はまだ有効ではない」→ ハンドシェイク失敗。さらに厄介なのは、この問題が特定の 2 台の組合せでだけ発生することで、再現が極めて困難です。解法は単純豪快——有効期限のウィンドウを最大まで引き伸ばす：

let mut params = rcgen::CertificateParams::new(vec![])?;
params.not_before = rcgen::date_time_ymd(2020, 1, 1);
params.not_after  = rcgen::date_time_ymd(2099, 12, 31);
// 证书与私钥以 DER 落盘，设备生命周期内复用，不再重签

🔑 信頼モデル：認証をアプリケーション層へ下ろす

証明書チェーン検証を諦めた後、両端にカスタム verifier（rustls の danger トレイト）を掛けます：クライアントは「サーバー証明書を何でも受け入れる」、サーバーは「クライアント証明書を強制要求」。TLS は暗号化だけを担い、身元認証は完全に上位層へ：

  • 各デバイスは初回起動時に自己署名証明書を生成し、CN フィールドにデバイス ID を書き込む
  • ハンドシェイク完了後、サーバーは相手のクライアント証明書 DER から CN を解析し、「認証済みデバイス身元」とする
  • すべての同期メッセージは、その ID が信頼リスト devices.json に存在することを要求し、メッセージ本体が名乗る id は無効
// 服务端：从客户端证书提取真实身份
fn cert_common_name(cert_der: &[u8]) -> Option<String> { /* 解析 CN */ }

// 消息处理时以证书 CN 为准，而非消息体里的 id
if !is_trusted(&cert_peer_id) {
    return reject("device not paired");
}

ペアリング自体は双方向の 6 桁ペアリングコードに頼ります：2 台のデバイスがそれぞれ画面にコードを表示し、ユーザーが互いに相手のコードを入力、双方向の照合が通って初めて信頼リストに書き込まれます。本質的には TOFU（Trust On First Use）+ 人手による帯域外検証の組合せで、セキュリティは Bluetooth ペアリングに相当します。

ついでに一つ補強：verify_tls12_signature で直接エラーを返し、TLS 1.2 を無効化して 1.3 ハンドシェイクのみを許可——ダウングレード攻撃の面を一つ減らします。

✅ テストでセキュリティモデルを固定

「カスタム verifier + アプリケーション層認証」のような設計は、リファクタリングの途中で静かに壊れやすいものです。そこで専用のリグレッションテストを書きました：偽装証明書 CN（信頼リスト外）の push は必ず拒否、未ペアリングデバイスの sync_push は必ずエラー、TLS ループバックハンドシェイクは必ず成功。セキュリティロジックを書いたら、あとはテストに見張りを任せましょう。

📝 まとめ

LAN のピアツーピア暗号化の正しい姿勢：自己署名証明書が身元を担い、TLS は暗号化だけを管轄し、認証はアプリケーション層に下ろし、ペアリングコードで TOFU を完結させ、有効期限ウィンドウを最大まで引き伸ばして時計ずれを許容。設計全体は VinePalmaFlow 内で約 300 行の Rust で、CA インフラを一切導入せずに、クラウドサービスに匹敵する通信安全を実現しています。
