Content fingerprints and incremental sync: why hand-write FNV-1a

📅 Aug 25, 2026⏱ ~11 min read
#Rust#Algorithms#Pitfalls#Sync

VinePalmaFlow's LAN sync started out with a strange phenomenon: two devices, having changed nothing, still transferred full data to each other on every sync. The logs showed every project's content fingerprint (hash) mismatching. Digging in, the root cause was hiding in a "feature" of the Rust standard library.

🔍 Root cause: DefaultHasher's random seed

The first implementation hashed project content directly with std::collections::hash_map::DefaultHasher. But Rust's RandomState deliberately randomizes its seed per process (a defense against hash-collision DoS). Which means:

// 进程 A
let mut h = std::collections::hash_map::DefaultHasher::new();
"project.md 内容".hash(&mut h);
// h.finish() = 0x9e37...

// 进程 B（同一份内容！）
// h.finish() = 0x51f2...  ← 完全不同的值

Incremental sync rests on the premise "same content → same fingerprint", and cross-process comparison is precisely the normal case in sync scenarios. DefaultHasher can't do that by design.

🛠️ Fix one: hand-write FNV-1a

We needed a hash that is deterministic across processes. A cryptographic hash (SHA-256) would do, but it's overkill for a local, trusted setting. FNV-1a is a few lines, and its avalanche behavior is plenty to tell file contents apart:

struct Fnv1a(u64);

impl Fnv1a {
    fn new() -> Self { Fnv1a(0xcbf29ce484222325) }
    fn update(&mut self, bytes: &[u8]) {
        for &b in bytes {
            self.0 ^= b as u64;
            self.0 = self.0.wrapping_mul(0x100000001b3);
        }
    }
}

The computed range is the project.md content plus the task files sorted by filename (filename + content), fed in one by one. Sorting is crucial — the filesystem guarantees nothing about directory-entry order; without sorting, two enumerations of the same directory already produce different fingerprints.

🛠️ Fix two: serialization must be idempotent

A deterministic hash alone isn't enough. The fingerprint's input is file content, and project.md's Front Matter is serialized out by ourselves. If serialization is unstable — say serde_yaml emits fields in enum order, or nulls appear and vanish — then the user merely opening and saving changes the file's bytes, the fingerprint follows, and we get yet another phantom diff.

So VinePalmaFlow hand-writes the Front Matter serialization: 15 fields in a fixed output order, null/empty-string/empty-array always stripped, unrecognized custom fields sorted last. The same metadata serializes byte-identically no matter the device or version. That's "idempotent serialization": serialize(parse(x)) == x.

🧩 Supporting machinery: baseline mirror & field-level merging

Fingerprints only solve "detecting differences"; "merging differences" relies on three-way merging. Under .localflow/sync/peers/{peer_id}/{project_id}/, every device keeps the baseline mirror (base) of the last sync result; merging compares the three sides:

Local vs basePeer vs baseResult
UnchangedChangedAccept the peer's
ChangedUnchangedKeep local
Both changed identicallyTake either
Both changed, differentlyConflict — hand it to the user

For project.md we add one more layer, field-level merging: the YAML Front Matter is merged three-way key by key, and the body gets its own textual three-way merge. If device A changes progress and device B changes the body, whole-file comparison would misjudge a conflict — field-level merging fuses them automatically. Only "the same field changed to different values by both sides" counts as a true conflict.

⚠️ A counter-intuitive detail: after resolving a conflict, update the base

The user picks "take theirs" in the conflict UI; if you only write back the target file, the base mirror still sits at the old version — at the next sync, from the peer's point of view your choice is yet another "new change", and the same conflict resurrects endlessly. The right move is to write the resolution into that peer's base directory at the same time:

fn resolve_conflict(...) {
    std::fs::write(target, content)?;
    // 更新基准镜像，本次选择成为新的共同基线
    write_base(&peer_base_dir(ws, peer_id, project_id), &file, content)?;
}

This bug was caught by our own tests before release — "the same conflict must not resurrect" is now a permanent regression case.

📝 Takeaways

The three cornerstones of incremental sync: deterministic hashing (FNV-1a) + idempotent serialization (fixed field order) + three-way merging (the base mirror advances with every resolution). Missing any one, they bite back as "phantom diffs" or "resurrecting conflicts" — the kind of failure that is maddening to trace. Now, when VinePalmaFlow's two devices sync at idle, the log is as quiet as if nothing had happened — exactly what we wanted.
