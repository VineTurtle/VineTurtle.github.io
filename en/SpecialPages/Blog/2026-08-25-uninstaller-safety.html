Designing a safe uninstaller: three layers that keep Linux deletions honest

📅 Aug 25, 2026⏱ ~11 min read
#Rust#Linux#Safe design#VinePalmaUninstaller

While developing VinePalmaUninstaller (our graphical Linux uninstaller), the question we hear most isn't "what can it uninstall" but "will it delete the wrong thing". For a tool whose core ability is deletion, safety isn't a feature — it's the bottom line. This note dissects our three lines of defense, plus the output-parsing pitfalls along the pkexec escalation road.

Defense one: the plan is the whitelist

Clicking "uninstall" doesn't execute commands directly. The backend first generates a complete uninstall plan: for APT packages it runs apt-get -s purge in simulation mode and parses out the to-be-removed package list; for leftover files, it lists every path slated for deletion. The front end shows this plan; the user ticks items and submits.

The crux: the ticks submitted by the front end are not trusted. At execution the backend regenerates the plan and intersects the submitted paths with the freshly regenerated one — not a byte outside the intersection gets touched. Even if someone forges a request past the interface submitting /etc/passwd, it isn't in the server-generated plan and gets dropped on the spot:

// 执行时：以服务端重新生成的计划为准
let plan = build_plan(pkg)?;               // 重新生成
let allowed: HashSet<_> = plan.files.iter().collect();
for path in user_selected {
    if !allowed.contains(path) { continue; }  // 不在计划内，忽略
    trash_or_delete(path)?;
}

Defense two: path blacklist & dangerous-component interception

Even if a path appears in the plan, a static blacklist still stands guard: /, /home, /etc, /usr, /var and 14 critical system directories plus their immediate children are refused outright; the "config roots themselves" under the user's home — .config, .cache, .local and so on — are also refused (the specific app directories inside them may be deleted); paths containing a .. component are ruled illegal on sight — a normal path never needs it, and whatever needs it is up to no good.

Defense three: protection switches & conservative default ticks

Residue scanning identifies an app's own directories via "package-name variant matching" (case-insensitive, hyphen/underscore equivalent), but matching comes in two grades: exact hits are ticked by default; fuzzy hits that merely "contain" the name are unticked by default — better to under-delete than to delete wrongly. The interface also carries "keep user config" and "keep system config" switches; ticked paths falling inside system directories are filtered out instantly. The three defenses each mind their own post: the whitelist governs "trusted origin", the blacklist governs "path legality", the switches govern "user intent".

🧪 The finicky art of escalation: pkexec & LC_ALL=C

System-level uninstall needs root, and we escalate dynamically with pkexec (a graphical password prompt, friendlier than sudo). A hidden pitfall here: apt's output wording depends on the locale — under a Chinese locale the localized prefixes are unparsable. The fix: force LC_ALL=C on every external command, then support all three English prefixes at once:

export LC_ALL=C
apt-get purge -y pkg
# 不同版本输出可能是：
#   Removing pkg ...
#   Purg pkg
#   Purging config files pkg
fn extract_removed(line: &str) -> Option<String> {
    for prefix in ["Removing", "Purg", "Purging"] { /* ... */ }
    None
}

Another detail: to check whether we're root, don't call getuid() — the Tauri process's environment variables can skew the libc result; parsing /proc/self/status's Uid: line directly is more reliable. Every external command is wrapped in a tokio timeout, so one stuck dpkg front end can't drag the whole interface down with it.

📊 Bonus: hand-parsing the dpkg database for risk

Risk levels (critical/high/medium/low) aren't guessed from package names; we parse /var/lib/dpkg/status directly: split into paragraphs by blank lines, continuation lines indented by spaces, only the install ok installed state counts; then we tally how many installed packages reverse-depend on each package, combined with the Essential and Priority: required fields to identify core components — Essential packages are marked critical straight away, packages depended on by 8+ others are marked high. Real data beats any heuristic.

📝 Takeaways

The safety design of deletion tools boils down to one sentence: the front end is untrusted, the plan is the whitelist, the blacklist is the safety net, defaults are conservative. When users hand their system to you, every knife you hand back must have a sheath.
