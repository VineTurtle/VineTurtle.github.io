アンインストーラーの安全設計：Linux で絶対に誤削除しない三重の防御

📅 2026年8月25日🕐 約 6 分
#Rust#Linux#安全設計#VinePalmaUninstaller

VinePalmaUninstaller（私たちの Linux グラフィカルアンインストーラー）を開発していて最もよく聞かれる質問は、「何をアンインストールできるか」ではなく「間違って削除しないか」です。削除を中核能力とするツールにとって、安全性は特性ではなく最低ライン。このノートは三重防御の設計と、pkexec 権限昇格の道で踏んだ出力解析の落とし穴を解きほぐします。

防御線 1：計画イコールホワイトリスト

「アンインストール」をクリックしても、コマンドが直接実行されるわけではありません。バックエンドがまず完全なアンインストール計画を生成します：APT パッケージは apt-get -s purge をシミュレーションモードで実行して削除対象のパッケージリストを解析し、残留ファイルは削除予定のパスを一件ずつ列挙します。フロントはこの計画を表示し、ユーザーがチェックして送信します。

肝心なのは：フロントが送信したチェック結果は信用されないことです。実行時、バックエンドは計画を再度生成し、送信されたパスと再生成した計画の積集合を取ります——積集合の外は 1 バイトも触れません。誰かが UI を迂回して /etc/passwd を送り込む偽装リクエストを組んでも、それはサーバー生成の計画に存在しないため、その場で棄てられます：

// 执行时：以服务端重新生成的计划为准
let plan = build_plan(pkg)?;               // 重新生成
let allowed: HashSet<_> = plan.files.iter().collect();
for path in user_selected {
    if !allowed.contains(path) { continue; }  // 不在计划内，忽略
    trash_or_delete(path)?;
}

防御線 2：パスブラックリストと危険コンポーネントの阻止

パスが計画に現れていても、静的ブラックリストがもう一枚構えます：/・/home・/etc・/usr・/var など 14 のシステム要諦ディレクトリと直系の子ディレクトリは一律拒否；ユーザーホーム配下の .config・.cache・.local など「設定ルートそのもの」の削除も拒否（中にある具体的なソフトのディレクトリは削除可）；.. コンポーネントを含むパスは即座に違法判定——正常なパスはそれを必要とせず、必要とするものは必ず悪意があります。

防御線 3：保護スイッチと保守的な既定チェック

残留走査は「パッケージ名バリアントマッチ」（大小文字を区別せず、ハイフン/アンダースコア等価）でソフト自身のディレクトリを特定しますが、マッチは 2 段階：完全一致は既定でチェック、「含む」関係だけのあいまい一致は既定で未チェック——削除し忘れるのはよくても、誤削除は許されません。UI には「ユーザー設定を保持」「システム設定を保持」の 2 つのスイッチもあり、チェックされたパスがシステムディレクトリに落ちていれば即座に除外します。3 本の防御線はそれぞれの持ち場を守る：ホワイトリストは「出所の信頼」、ブラックリストは「パスの合法性」、スイッチは「ユーザー意図」を管轄します。

🧪 権限昇格の勘所：pkexec と LC_ALL=C

システムレベルのアンインストールには root が要り、pkexec で動的に権限昇格します（グラフィカルなパスワードダイアログが出て sudo より親切）。ここには隠れた落とし穴があります：apt の出力文言はロケールに依存し、中国語環境では現地語の接頭辞が解析できません。解法は、すべての外部コマンドに LC_ALL=C を強制し、その上で 3 種の英語接頭辞に同時互換を持たせること：

export LC_ALL=C
apt-get purge -y pkg
# 不同版本输出可能是：
#   Removing pkg ...
#   Purg pkg
#   Purging config files pkg
fn extract_removed(line: &str) -> Option<String> {
    for prefix in ["Removing", "Purg", "Purging"] { /* ... */ }
    None
}

もう一つの細部：自分が root かどうかの判定に getuid() を呼ぶのは避けましょう——Tauri プロセスの環境変数が libc の結果に干渉することがあり、/proc/self/status の Uid: 行を直接解析する方が確実です。すべての外部コマンドは tokio の timeout で包み、固まった dpkg フロントエンド 1 個に UI 全体を引きずり殺されないようにします。

📊 おまけ：dpkg データベースを手解析してリスク算出

リスク等級（critical/high/medium/low）はパッケージ名の推測ではなく、/var/lib/dpkg/status を直接解析します：空行で段落分割、スペースインデントの継続行、install ok installed 状態だけを認め、各パッケージがインストール済みパッケージから逆依存されている数を集計し、Essential と Priority: required フィールドと合わせてコアコンポーネントを判定——Essential パッケージは即 critical、8 個以上のパッケージから依存されるものは high。実データはあらゆるヒューリスティックに勝ります。

📝 まとめ

削除系ツールの安全設計は一言にまとめられます：フロントは信用しない、計画はホワイトリスト、ブラックリストが最後の防壁、既定値は保守的。ユーザーはシステムをあなたに預けます。あなたが返すナイフの一本一本に、鞘がなければなりません。
