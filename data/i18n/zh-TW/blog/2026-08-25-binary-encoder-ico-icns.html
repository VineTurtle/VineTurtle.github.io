給 VinePalmaToolbox 做「圖片格式轉換」工具時遇到了一個尷尬：瀏覽器 Canvas 的 toBlob() 只支援 PNG / JPEG / WebP，而使用者偏偏最常要求「把這張圖轉成 ICO 圖示」。找遍 npm，好用的 ICO 編碼庫寥寥無幾，ICNS（macOS 圖示）更是沒有維護良好的純前端實現。最後我們決定：照著格式規範，用 DataView 一個位元組一個位元組自己拼。

🧱 ICO：最「簡單」的容器格式

ICO 本質是一個「PNG 打包器」：檔案頭 + 目錄 + 圖片資料。Vista 之後允許直接內嵌 PNG 資料，這大大簡化了實現——用 Canvas 把原圖縮放到各尺寸匯出 PNG，再拼裝即可：

// 文件头：6 字节，小端
writeU16(0);        // 保留字段，必须为 0
writeU16(1);        // 1 = ICO，2 = CUR
writeU16(count);    // 目录项数量

// 每个尺寸一个目录项：16 字节
writeU8(size === 256 ? 0 : size);  // 宽（256 写 0！）
writeU8(size === 256 ? 0 : size);  // 高
writeU8(0);          // 调色板数
writeU8(0);          // 保留
writeU16(1);         // 色彩平面（ICO）
writeU16(32);        // 色深
writeU32(png.length);// 数据长度
writeU32(offset);    // 数据偏移

三個容易翻車的細節：① 256px 的寬高要寫 0 而不是 256（一個位元組裝不下，規範約定 0 表示 256）；② 偏移量必須累加計算，目錄區之後第一個資料塊的偏移是 6 + 16×count；③ ICO 與 CUR 的區別除了型別欄位，CUR 還要把「色彩平面/色深」欄位改寫為熱點座標（hotspot x/y）——滑鼠指標的點選位置就存在這兩個欄位裡。

🍎 ICNS：大端序的另一套世界

ICNS 是 macOS 的圖示格式，與 ICO 最大的不同是大端序，以及用 4 位元組 ASCII 型別碼標識尺寸：

writeU32(0x69636e73);  // 'icns' 魔数（大端）
writeU32(totalLength); // 整个文件长度
// 每个尺寸一个块：
// 4 字节类型码 + 4 字节块长 + PNG 数据
writeType('icp4');   // 16x16
writeType('ic07');   // 128x128
writeType('ic10');   // 512x512（或 1024@2x）

除錯時最費時間的是「檔案長度」欄位：必須等於所有塊長之和加 8 位元組頭，寫錯一個位元組 macOS 直接拒絕載入，而且不報錯。

🔍 通用經驗：用十六進位制編輯器驗收

二進位制程式碼的正確性沒法 console.log 出來看。我們的驗收流程是：生成檔案 → xxd 檢視頭十六個位元組 → 對照 spec 逐欄位核對 → 再用系統工具（file 命令、macOS 預覽、Windows 資源管理器）交叉驗證。file x.ico 輸出 "MS Windows icon resource - 5 images" 的那一刻，比任何單元測試都踏實。

📝 小結

這輪手搓的收穫：二進位制格式沒有想像中神秘——ICO 是「陣列 + 偏移」，ICNS 是「TLV 列表」，真正的工作量在於邊界約定（256 寫 0、長度含頭不含頭、大端小端）。這些約定在 spec 裡往往只有半句話，卻是全部的坑所在。VinePalmaToolbox 的圖片轉換工具現在支援 PNG/JPEG/WebP/BMP/ICO/CUR/ICNS/DDS 互轉，全部核心編碼邏輯不超過 400 行 TypeScript。
